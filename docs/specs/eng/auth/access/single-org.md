# Stage 2: Single-Org

> **Status: design only (DEC-042, DEC-047, DEC-050).** Built only if a project is at **stage 2** ([README.md §3](README.md)). This file holds the organization core (§1–9, §11–14) and the one-hidden-organization setup (§10). The SaaS multi-tenant layer reuses everything except §10: [saas/multi-tenant.md](../../saas/multi-tenant.md). Moving here from stage 1: [migration.md §3](migration.md) (Step A).

Better Auth names come from the organization plugin docs and the `organization-best-practices` skill as of 2026-11. Everything marked *verify* must be checked against the installed version before use.

## 1. What this stage gives

- Roles stored in the database and created at runtime (Better Auth **dynamic access control**), while the permissions stay in code.
- The same module `permissions.ts` statements as stage 1. Modules do not change shape.
- An `organization_id` on every module table from day one (DEC-044), so moving on to multi-tenancy ([saas/migration.md](../../saas/migration.md)) needs no data migration.
- Two separate layers: **platform** (`user.role`, admin plugin, §8) and **organization** (`member.role`, organization plugin, §4–7) ([README.md §5](README.md), DEC-043).
- To users the app looks the same as at stage 1: there is one organization and it is never shown.

## 2. Plugin setup

```ts
// packages/auth/src/server.ts (sketch)
plugins: [
  admin({ ac: platformAc, roles: platformRoles, defaultRole: 'user' }),   // platform layer only (§8)
  organization({
    ac: orgAc,
    roles: orgRoles,                       // code roles: owner, admin, member (+ custom code roles)
    creatorRole: 'owner',
    dynamicAccessControl: {
      enabled: true,
      maximumRolesPerOrganization: 20,     // *verify* option name
    },
    teams: { enabled: false },
    disableOrganizationDeletion: true,     // soft delete only (multi-tenant.md §8)
    allowUserToCreateOrganization: false,  // stage 2; multi-tenant overrides (saas/multi-tenant.md §2)
    schema: {
      organization: { additionalFields: { status: { type: 'string', required: true, defaultValue: 'active' } } },
    },
    hooks: { /* audit events, §13 */ },
  }),
]
```

- Client: `organizationClient()` added next to `adminClient()`. *Verify* whether the client needs `ac`/`roles` for `checkRolePermission`; we do not use it (the web app reads `/api/me/permissions` only).
- Import from the plugin's own path (`better-auth/plugins/organization`, *verify* the dynamic access control import path).
- Plain `adminUserIds` stays unset (DEC-032).

## 3. Schema added

Generated by the Better Auth CLI, then migrated with Drizzle Kit like the rest ([DATABASE.md §3](../../DATABASE.md)).

| Table / column | Purpose |
|:---|:---|
| `organization` | `id`, `name`, `slug` (unique), `logo`, `metadata`, `created_at`, plus our `status` (`active`, `suspended`, `deleted`) |
| `member` | `id`, `organization_id`, `user_id`, `role` (comma-separated, no spaces), `created_at`. One row per user per organization |
| `invitation` | Invitations. Stays empty at stage 2 |
| `organization_role` | Runtime roles: `organization_id`, `role` (name), `permission` (JSON), timestamps (*verify* table and column names) |
| `session.active_organization_id` | The organization every permission check uses |

`member.role`, like `user.role`, is not a foreign key. Code roles are not stored in `organization_role`.

## 4. Access control

`apps/api/src/utils/auth/access.ts` builds two access controls:

```ts
// sketch
const moduleStatement = mergeStatements([postsPermissions /* , new modules */])  // throws on duplicates

// Organization layer: plugin defaults + every module
export const orgAc = createAccessControl({ ...orgDefaultStatements, ...moduleStatement })
export const orgRoles = {
  owner:  orgAc.newRole({ ...orgDefaultStatements, ...moduleStatement }),   // everything
  admin:  orgAc.newRole({ ...orgAdminDefaults, ...mergeGrants(modules, 'admin') }),
  member: orgAc.newRole({ ...mergeGrants(modules, 'member') }),
}

// Platform layer: only the platform statement (§8.2)
export const platformAc = createAccessControl(platformStatement)
export const platformRoles = {
  super_admin: platformAc.newRole(platformStatement),
  user:        platformAc.newRole({}),
  // custom platform code roles, e.g. platform_support (§8.1)
}
```

- `orgDefaultStatements` are the plugin's own resources (`organization`, `member`, `invitation`, `team`, `ac`). `ac:create|read|update|delete` controls runtime roles (*verify* names). We list the defaults we use explicitly, as the admin module does for the admin plugin.
- Module `grants` are keyed by **organization code roles**: `owner` (derived: everything), `admin`, `member`, plus any custom code role.
- Module resources never go into `platformStatement`, and platform resources never go into `orgAc`. A startup check fails if a key appears in both.
- The default for a new member is `member`.

### 4.1 Default organization matrix

| Permission | `owner` | `admin` | `member` |
|:---|:---:|:---:|:---:|
| `posts:read`, `posts:write` (own) | ✅ | ✅ | ✅ |
| `posts:manage_all` | ✅ | ✅ | ❌ |
| `member:read` (list members) | ✅ | ✅ | ❌ |
| `member:update` (change roles) | ✅ | ✅ | ❌ |
| `ac:read` (see roles) | ✅ | ✅ | ❌ |
| `ac:create`, `ac:update`, `ac:delete` (runtime roles) | ✅ | ❌ | ❌ |
| `organization:update` (rename, logo) | ✅ | ❌ | ❌ |

## 5. Module data is scoped by organization

Applies at stage 2 and in the SaaS multi-tenant layer (DEC-044).

- Every module table gets `organization_id text not null references organization(id)`, indexed first in its main indexes (`idx_post_org_created (organization_id, created_at desc)`).
- Uniqueness becomes per organization: `post.slug` → `unique (organization_id, slug)`.
- The `auth` macro resolves `ctx.org = { id }` from `session.activeOrganizationId`. A route that needs data and has no active organization returns `403 NO_ACTIVE_ORGANIZATION`.
- Every repository function takes `orgId` as its **first** argument and puts it in every `where`, `insert` and `update`. A repository function without it does not compile (typed helper `scoped(orgId)`).
- `scoped(orgId)` is the **only** way module code reaches a module table: no direct `db` import in `modules/*` (lint rule). Multi-tenancy adds database row-level security inside this one helper, without touching repositories ([saas/architecture.md §4](../../saas/architecture.md), DEC-051). Stage 2 has no RLS: with one organization it would protect nothing.
- A record from another organization is **not found** (`404`), never `403`: the response must not confirm it exists.
- Cache keys start with the organization: `org:{orgId}:posts:list:...`. Cache invalidation is per organization.
- Log context adds `organizationId` to every line inside an organization-scoped route ([observability/README.md](../../observability/README.md)). Never the organization name.
- Only functions named `*AcrossTenants` may skip the filter, and only the `platform` module may call them ([saas/platform-console.md §6](../../saas/platform-console.md)).
- **Platform tables are not scoped.** `user`, `session`, `account`, `verification` and `feature_flag` belong to the whole app and have no `organization_id` (DEC-048).

## 6. Permission checks

- `{ permission: 'posts:write' }` calls the organization plugin's `hasPermission` with the session headers, for the active organization (*verify* `auth.api.hasPermission({ headers, body: { permissions } })`). No active organization → `403 NO_ACTIVE_ORGANIZATION`.
- One permission per call, as at stage 1: with several roles, a check passes only if **one** role grants all of it.
- `{ platformPermission: 'user:ban' }` is a separate macro option for platform routes (§8). The two options cannot be mixed on one route.
- Runtime role lookups are cached in Redis per organization (`org:{orgId}:roles`, TTL 5 minutes) and cleared after any role change (§7). *Verify* whether the plugin already caches; if it reads the database on every check, our cache wraps it.
- `GET /api/me/permissions` returns:

```ts
{
  organization: { id, slug, name } | null,
  roles: string[],                  // member.role in the active organization
  permissions: Permission[],        // organization permissions
  platformRoles: string[],          // user.role
  platformPermissions: PlatformPermission[],
}
```

The web app's `can()` reads `permissions`; `canPlatform()` reads `platformPermissions`.

## 7. Runtime roles (dynamic access control)

| Action | Endpoint (*verify*) | Needs |
|:---|:---|:---|
| List roles | `GET /api/auth/organization/list-roles` | `ac:read` |
| Create role | `POST /api/auth/organization/create-role` | `ac:create` |
| Update role | `POST /api/auth/organization/update-role` | `ac:update` |
| Delete role | `POST /api/auth/organization/delete-role` | `ac:delete` |
| Assign role | `POST /api/auth/organization/update-member-role` | `member:update` |

Rules (plugin behaviour marked *verify*; where the plugin does not enforce it, our `hooks.before` does):

| Rule | Error |
|:---|:---|
| Role name is `snake_case`, 2–40 chars, and not a code role or platform role name | `400 INVALID_ROLE_NAME` |
| Every permission in the role exists in `orgAc` (plugin) | `400` (plugin code) |
| You cannot grant a permission you do not hold yourself (*verify*) | `403 CANNOT_GRANT_UNHELD_PERMISSION` |
| A role still assigned to a member cannot be deleted (plugin) | `400` (plugin code) |
| Code roles (`owner`, `admin`, `member`, custom code roles) cannot be edited or deleted | `400 SYSTEM_ROLE` |
| Nobody changes their own member role | `400 CANNOT_CHANGE_OWN_ROLE` |
| Only an `owner` assigns or removes `owner`; the last owner keeps it (plugin) | `403` / plugin code |
| More than `maximumRolesPerOrganization` runtime roles | plugin code |

When the code statement loses an action, runtime roles that still list it keep working for the rest and the API emits `access.stale_permission` (warn) at startup with the role IDs.

## 8. Platform layer

The part of the admin plugin that stays from stage 2 on. It answers "who runs the app itself" and grants **no** module permissions (DEC-043). The SaaS multi-tenant layer adds the platform console on top of it ([saas/platform-console.md](../../saas/platform-console.md)).

### 8.1 Platform roles

Defined in code with the admin plugin, exactly like stage 1 roles ([static-roles.md §2](static-roles.md)):

| Role | Purpose |
|:---|:---|
| `super_admin` | Everything in the platform statement |
| `user` | Default. No platform permissions |
| Custom, e.g. `platform_support` | Optional, in code: read-only access for support staff |

`user.role` never holds an organization role. A startup check emits `access.unknown_platform_role` (warn) for any other value.

### 8.2 Platform statement

`apps/api/src/modules/platform/permissions.ts`:

```ts
// sketch
export const platformPermissions = definePlatformPermissions({
  statement: {
    user:         ['list', 'get', 'ban', 'set-role', 'set-password', 'delete'],   // admin plugin built-ins we use
    session:      ['list', 'revoke'],
    feature_flag: ['read', 'write'],      // when flags are adopted (DEC-048)
    // multi-tenant (SaaS) adds platform_org and platform_audit (saas/platform-console.md §3)
  },
  grants: {
    platform_support: { user: ['list', 'get'], session: ['list'], feature_flag: ['read'] },
  },
})
```

- The impersonate actions are left out (DEC-032).
- Routes use `{ platformPermission: 'user:ban' }`, checked with the admin plugin's `userHasPermission`.

### 8.3 Endpoints

Users and sessions keep the admin plugin endpoints and guard rules of [static-roles.md §7](static-roles.md): `list-users`, `get-user`, `ban-user`, `unban-user`, `set-role`, `set-user-password`, `remove-user`, `list-user-sessions`, `revoke-user-session`, `revoke-user-sessions`. `set-role` accepts only platform roles.

| Method | Path | Needs | Result |
|:---|:---|:---|:---|
| GET | `/api/platform/users/:id/memberships` | `user:get` | `{ organizationId, roles, createdAt }[]` (one row at stage 2) |

Feature flag management routes move to `platformPermission` ([feature-flags/access-stages.md §3](../../feature-flags/access-stages.md)).

### 8.4 Rules

1. **A platform role grants no organization permissions**, and an organization role grants no platform permissions.
2. **Writes need a fresh session** (`freshAge`, 1 hour, [auth/README.md §2](../README.md)): otherwise `403 SESSION_NOT_FRESH`, and the web app asks the user to sign in again.
3. **No impersonation** and no "log in as user" (DEC-032).
4. **No self-targeting:** you cannot ban yourself or change your own platform role.
5. **At least one `super_admin`** always remains.
6. Every platform write emits its audit event (§13).

### 8.5 Web

The `platform` feature, under a separate `/platform` layout with a visible "Platform" banner. Links to it appear only when `canPlatform()` is true; a direct visit without permission redirects to the home page.

| Page | Needs |
|:---|:---|
| `/platform/users`, `/platform/users/:id` (profile, sessions, ban, platform role) | `user:list` / `user:get`, `user:ban`, `user:set-role`, `session:*` |
| `/platform/feature-flags` (when flags are adopted) | `feature_flag:read` / `feature_flag:write` |

These pages replace the users pages of the stage 1 `admin` feature (F-03). The SaaS multi-tenant layer adds organization and audit pages ([saas/platform-console.md §7](../../saas/platform-console.md)).

## 10. Stage 2 only: one hidden organization

One organization, created by the seed, never shown to users. Every user is a member of it. The SaaS multi-tenant layer **replaces this whole section** with [saas/multi-tenant.md](../../saas/multi-tenant.md).

### 10.1 Configuration

| Concern | How |
|:---|:---|
| The organization | Seed or migration creates it with `auth.api.createOrganization({ body: { name, slug: 'app', userId: superAdminId } })`; the first `super_admin` becomes its `owner`. *Verify* this works with `allowUserToCreateOrganization: false` |
| Finding it | Env `PRIMARY_ORG_SLUG` (default `app`). Startup looks it up and caches its ID; startup **fails** if it is missing |
| New users join it | `databaseHooks.user.create.after` → `auth.api.addMember({ body: { userId, organizationId, role: 'member' } })` |
| Active organization always set | `databaseHooks.session.create.before` returns the session with `activeOrganizationId` = the primary organization |
| No other organizations | `allowUserToCreateOrganization: false`; create, delete, set-active, leave and invitation paths are not in the allowlist |
| Removing someone | Not through the organization: a platform ban (§8) |

At startup the API counts users without a `member` row in the primary organization and emits `access.member_missing` (warn). They can sign in but have no module permissions until fixed with `bun run access:repair` (adds missing rows as `member`).

### 10.2 Who does what

| Person | Platform role | Organization role |
|:---|:---|:---|
| You, running the app | `super_admin` | `owner` |
| Staff who manage content and members | `user` | `admin` or a runtime role |
| Everyone else | `user` | `member` |

### 10.3 Allowed organization endpoints

`get-active-member`, `list-members`, `update-member-role`, `has-permission`, `list-roles`, `get-role`, `create-role`, `update-role`, `delete-role` (all under `/api/auth/organization/`; *verify* exact paths in ORG-01 and record them in [API.md](../../API.md)).

### 10.4 Web

| Feature | Page | Needs |
|:---|:---|:---|
| `settings` | `/settings/members`: list members, change a member's role | `member:read` / `member:update` |
| `settings` | `/settings/roles`: list, create, edit, delete runtime roles; code roles shown read-only | `ac:read` / `ac:create`, `ac:update`, `ac:delete` |
| `platform` | §8.5 | platform permissions |

The role editor shows the statement grouped by module, with only the permissions the current user holds selectable.

### 10.5 Sign-up and sign-in

Unchanged from [auth/README.md §4](../README.md), plus: a new user is added to the primary organization as `member` before their first session is created, so their first request already has permissions. A user whose `member` row is missing gets `403 NO_ACTIVE_ORGANIZATION` on module routes, not a crash.

## 13. Audit events

Emitted with `module: "auth"` (organization) or `module: "platform"` (platform layer). IDs only, never names or emails.

| Event | Payload |
|:---|:---|
| `audit.org.member_added` | `organizationId, userId, role, actorId?` |
| `audit.org.member_role_changed` | `organizationId, userId, from, to, actorId` |
| `audit.org.member_removed` | `organizationId, userId, actorId` |
| `audit.org.role_created` / `role_updated` / `role_deleted` | `organizationId, roleId, roleName, permissionCount, actorId` |
| `audit.user.banned`, `audit.user.role_changed`, `audit.session.revoked` | As in [auth/README.md §6](../README.md) |

Multi-tenant and the platform console add their own ([multi-tenant.md §12](../../saas/multi-tenant.md), [saas/platform-console.md §8](../../saas/platform-console.md)).

## 14. Tests

In `apps/api/tests/utils/auth/`, `apps/api/tests/modules/platform/` and `apps/api/tests/modules/<module>/`:

- **Organization matrix:** each organization code role × every protected route → expected status. A runtime role with one permission → only that route passes.
- **Platform matrix:** `super_admin`, `platform_support`, `user` × every platform route.
- **Layer test:** a `super_admin` who is not a member gets 403 on module routes; an `owner` with platform role `user` gets 403 on platform routes.
- **Runtime roles:** every rule in §7, including granting an unheld permission and deleting an assigned role. A role change applies on the next request (cache cleared).
- **Scoping:** with two organizations in the test database (even at stage 2), a member of A gets 404 for B's records and never sees them in lists ([multi-tenant.md §13](../../saas/multi-tenant.md) is the full suite).
- **Stage 2 hooks:** a new user gets a `member` row and their first session has `activeOrganizationId`; startup fails without the primary organization.
- **Platform rules:** stale session → `403 SESSION_NOT_FRESH` on writes; self-ban and own-role change refused; last `super_admin` kept.
- **Allowlist:** every organization path not in §10.3 → 404.
